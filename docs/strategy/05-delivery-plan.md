## 1. 推荐顺序与投入

| 顺序 | 交付 | 优先级理由 | 粗略投入范围 |
|---|---|---|---|
| G0 | 当前开发版可靠性收口 | 上轮新接口和进度需要补边界证据 | 1–3 个开发日 |
| G1 | 来源先行、轻量阅读器、准确配置提示 | 首次使用与结果利用最直接 | 2–4 个开发日 |
| G2 | 存储写入口与显式任务恢复 | 避免重做、丢状态，支撑后续扩展 | 3–6 个开发日 |
| G3 | 笔记与原转录对照 | 差异化主线，有可复用数据基础 | 3–6 个开发日 |
| G4 | 质量样例集、发布环境与诊断 | 让改动可评价、支持成本可控 | 2–5 个开发日 |
| G5 | 历史性能与可选全文索引 | 根据测量扩展，避免过早架构 | 1–3 日基准；索引另估 |

估算包含实现、测试、Review，不承诺固定时长或某个模型能一次完成。G4 的离线样例准备可提前；G5 的性能测量可与 G1 独立进行。版本号在选定实际交付后再定，不给六个门禁预分配六个版本。

## G0 当前开发版发布前收口

目标：上轮功能对外表述与实际行为一致，文件打开仅落在预期 Markdown 范围。

允许涉及：`backend/main.py`、`frontend/script.js`、相关 API/前端测试、对应文档；必要时新增小型 `backend/result_access.py` 或 `task_progress.py`。不同时搬迁全部路由。

实施步骤：

1. 保存 dirty diff 基线，确认仍在 `codex/beta4-progress-result-loop`；不覆盖或重置上轮成果。
2. 先验证 `.md` 类型、解析前链接/父路径、损坏清单等文件打开边界。写出失败用例后修复，优先复用现有附件安全检查模式。
3. 构造多 P、未知时长、迟到回调、取消、模型加载与 Paraformer 序列。确定进度单调范围；ETAs 明示仅当前阶段，未知显示未知。
4. 修改 readiness 词义：已填/已保存不等于鉴权成功，pending 不等于就绪。检查字幕导入无需 ASR/笔记模式无需误导性模型承诺。
5. 核对隐私文案和发布说明；修正错误陈述，不引入新的网络探测。

验收：所有上述用例通过；原有模板/目的地/导出不变；危险目标从未交给系统打开；用户看得到 ETA 范围和阶段；721/3 旧回归无未解释失败。若系统无权限测试 link，记录实际测试缺口并在受支持主机补验收，不能只留跳过就宣称安全闭环。

退出：源代码本地可审查。便携构建、实际文件打开交互、发布必须按当前授权核对；若未经批准，本任务不自动升级版本。

## 2. 推荐的第一次六小时开发窗口

只执行 G0，不预设六小时完成全部产品升级：

| 时间盒 | 内容 | 必须留下的成果 |

| 0–45 分钟 | 基线、边界测试、失败复现 | 可重复的失败证据与影响范围 |

发现高风险缺陷时停止排后续功能，先完成最小修复。时间盒只是资源安排，不能据此标记完成；没有达到验收门禁的任务维持进行中。

## 6. 后续可选方向的决策门槛

- Headless：有明确 Agent 冷启动需求时审查上游实现，定义进程所有权/空闲退出；不与 G0 混合。
- 平台扩展：目标用户给出真实样本和使用频率，先测现有 yt-dlp；专项适配、登录与费用另立合同。
- 批量处理：恢复、取消与幂等验证后先做 5–10 条上限试验，提交前逐条确认。
- 多语言：先中文流程稳定，外部用户验证英文需求后再翻译 UI；README 双语不代表 UI 已国际化。
- 商业化：等有实际持续使用再讨论签名安装包、技术支持或模板服务；下载数和 Stars 不当付费需求证明。
- 简历展示：可记录需求取舍、差异化实现、故障复现、质量评测和发布证据；明确上游派生，不声称从零实现 Whisper/下载器，也不虚构用户规模或节省时间。
