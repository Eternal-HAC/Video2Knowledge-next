## 交付与证据口径

- `scripts/benchmark_history.py`：离线创建 100 / 1,000 / 10,000 个合成清单；
  默认、组合筛选、收藏和第二页四种查询，每种 7 次暖态采样，记录原始值、p50/p95、读取次数、
  响应摘要；另测首次查询、启动恢复及 Python 跟踪分配峰值。
- 不启动服务器，不创建事件循环或浏览器，不调用 LLM/ASR/下载/飞书；应用导入前禁用 dotenv，
  工作区/缓存强制隔离；网络连接和外部进程有本进程阻断保护。
- 计时不包含读取计数或 tracemalloc；计数只表示成功的 Python Path.open 读句柄，
  不含 stat / 目录扫描 / 缺失打开尝试 / 物理 IO。内存不是 RSS，首次查询不是冷磁盘。
- nearest-rank 的 7 样本 p95 等于最大值。系统后台负载没有隔离，结果仅描述本机本次合成数据，
  不保证跨设备或真实大历史成绩。
- 设备：Windows 11，AMD Ryzen 7 7840HS，16 个逻辑处理器，Python 3.13.7。
  未修改电源/安全软件设置，未测 EXE、HTTP/DOM 或整机物理内存。

方法、限制与复现命令见 [历史基准说明](../quality/history-benchmark.md)。

最小改动仅在 `backend/main.py`：

1. `_read_history_manifest` 使用已经校验并规范化的目录，直接调用现有 repository reader；

2. `_history_task_record` 同时返回摘要和本次清单快照；列表判断 agent/web 可见性直接用该快照。

3. 列表只保留可见摘要，不先保存全量摘要再重新读所有清单；每任务每请求一读、一规范化。

这也避免“摘要使用第一次清单、隐藏规则使用第二次清单”的请求内不一致。
没有缓存跨请求结果，没有修改存储格式、预加载上限、搜索/分页、收藏写入或删除策略。

## 决策与下一候选

1,000 条优化后默认暖态 p95 为 1011.433ms，仍高于 300ms 的参考目标。
本轮证明重复读取可减少，不证明现有全扫描架构达到大历史交互目标。
不减少可查询历史、不隐藏旧任务、不改 total/分页口径来降低耗时，也不静默加入数据库。

下一候选为受限历史摘要缓存/可重建索引的独立设计与验收合同，尚未实施：

- 保持 task.json/Markdown 为依据，只保存查询需要的摘要，不缓存正文或凭据。
- 先定义缓存失效：收藏/进度/发布/删除、本进程 repository 更新、外部文件替换、
  损坏后恢复、工作区切换和未预加载任务；需要明确外部同 mtime/size 修改的识别/刷新边界。
- 写入口统一失效、显式全量刷新、重启重建和损坏回退都有测试，不能为了速度返回过期收藏或幽灵任务。
- 再测相同输入与查询；元数据需求先评估有界缓存，全文搜索明确需要时再评估标准库 SQLite FTS。
- 后台扫描/线程化还须验证 live tasks 并发语义及 HTTP 响应，不能只把同步扫描扔进线程就算完成。

Host/Origin、打包态验收、真实 Provider 评测及发布仍走独立授权；没有因 G5 自动启动。
